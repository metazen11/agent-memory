**Important validator-suite caveat:** v1 used a synthetic
`IN_DISTRIBUTION_PROMPTS` ("Call tool 'X' with appropriate arguments.")
which v2 was explicitly trained NOT to memorize. The suite was rewritten
during this run with realistic single-turn prompts. v2's training data
is predominantly multi-turn session continuations, so single-turn
aggregate is **conservative against v2**. The chat-loop test (below) is
the authoritative gate for production behavior.

## Validator regression

`scripts/fine_tune/validate_tool_calls.py` was found to have THREE bugs
during Phase 4 that prevented v2 from being measured correctly. All
fixed in this run:

1. **Line 63** — hardcoded to load `v1/tool_schemas.json`; now auto-picks
   the latest available dataset version (`v2` if present, falls back to
   `v1`).
2. **Line 77** — overrode real tool descriptions with
   `"Tool 'X' (schema inferred from training data)."` placeholder text;
   now uses the real descriptions from `tool_schemas.json` when present.
3. **Line 264** — system prompt was missing the `"with access to tools."`
   suffix that's in the v2 training data; the rendered prompt didn't
   match what the model was trained on. Now matches.
4. Bonus: `IN_DISTRIBUTION_PROMPTS` was the v1 synthetic shape. Replaced
   with realistic single-turn prompts. Docstring documents the
   single-turn limitation.
5. Bonus: `pyrightconfig.json` added, pointing Pyright at the
   `.venv-finetune` so torch/transformers imports resolve cleanly.

These are independent code-quality wins that benefit all future runs.

## Known gaps + follow-ups

1. **32k context ceiling** — base Qwen2.5-3B's positional encoding caps
   at 32,768 tokens. v2 inherits this. YaRN at serve time can extend to
   128k+ at small quality cost; recommended only for sessions that
   regularly approach 24k+ of context. See FAILURE_MODES #12.
2. **No vision** — Qwen2.5-3B-Instruct is text-only. v3 should pick a
   base that satisfies long-context + vision + tool-calling
   simultaneously. Scoping doc pending.
3. **MPS training is slow** — 12h 38m for 1 epoch on 23k rows is the
   bottleneck. Cloud A100 (Runpod, ~$10) would do the same job in ~50 min.
4. **`empty_args_emissions_total` counter not wired into `/api/stats`** —
   currently only logged in the validator JSON. Wiring to live stats is
   a separate task.
