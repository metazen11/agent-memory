# v3 Full-Run Incident — 2026-05-15 / 2026-05-16

**Status:** Mitigated, retrain in progress (started 2026-05-16 06:03 PDT)

**Authors:** mz + Claude

## TL;DR

The v3 full-training run started 2026-05-15 22:50 UTC died ~7h in with no
Python traceback; the macOS host rebooted 42 minutes later. Diagnosis
revealed **two independent failures stacked**:

1. **Dropbox-mounted training paths.** `models/` and `.venv-finetune/`
   were symlinks into `~/Dropbox/_CODING/agentMemory/`. Every
   checkpoint (~400 MB every 250 steps) and every Python import was
   contesting Dropbox's sync engine. Pre-existing
   `*conflicted copy*.log` files in `logs/` were direct evidence the
   path had been corrupted by sync race conditions before. This
   violated the host CLAUDE.md's source-of-truth rule
   ("Source of truth: ~/_CODING/ local SSD — no cloud sync
   conflicts").
2. **NaN eval_loss from step 500 onward.** Every evaluation
   (steps 500/1000/1500/2000) returned `eval_loss: nan`. HF Trainer's
   "best checkpoint" tracker silently stayed at `best_metric=None`
   throughout, so we had no useful mid-run signal. Training loss
   itself looked healthy (1.3 → 0.7).

Run stopped mid-eval at step 2500/5723 (~44% complete) without
flushing a Python traceback to disk. System rebooted 42 minutes
later.

## What broke and how

### Failure 1 — Dropbox-backed training paths

**Discovery:** `readlink -f models` resolved to
`/Users/mz/Dropbox/_CODING/agentMemory/models`. Same for
`.venv-finetune/`. Repo root was correctly on local SSD.

**Mechanism:** Every `save_steps=250` write produced a ~400 MB
checkpoint dir (`adapter_model.safetensors` + `optimizer.pt`) inside
the Dropbox-watched tree. Dropbox sync indexed each one, racing
against the next checkpoint write. The MPS/SoC was already at high
load. The cumulative I/O pressure manifested as a frozen Python
process, then a system reboot.

**Resolution:** `mv` both targets onto local SSD (same APFS volume,
so the operation was a near-instant inode rename — 0.005s total for
63 GB).

```bash
rm models .venv-finetune                                    # remove symlinks
mv ~/Dropbox/_CODING/agentMemory/models       ./models
mv ~/Dropbox/_CODING/agentMemory/.venv-finetune ./.venv-finetune
# fix venv script shebangs (59 files baked-in the old path)
sed -i '' "1s|/Users/mz/Dropbox/_CODING/agentMemory/.venv-finetune|/Users/mz/_CODING/agentMemory/.venv-finetune|" .venv-finetune/bin/*
```

### Failure 2 — NaN eval_loss

**Initial hypothesis (wrong):** MPS + bf16 numerical instability in
eval forward pass. Tried `Fp32EvalTrainer` subclass that cast model
→ fp32 for the eval step → bf16 after. Retrain #1 hit the **exact
same NaN at step 500** despite the fp32 cast. Hypothesis falsified.

**Actual root cause:** 109/1392 valid samples (7.8%) and 840/22890
train samples (3.7%) produce **zero predicted tokens** after the
trainer's assistant-only label masking. With
`per_device_eval_batch_size=1` and `CrossEntropyLoss(ignore_index=-100)`,
a sample with all labels=-100 returns `loss = NaN` (division by zero
when averaging over zero non-ignored tokens). Even one such sample
poisons the mean.

**Why these rows are empty:** Investigation of the flagged rows
revealed they are NOT empty assistant turns. They are rows where the
user prompt is long (e.g. lengthy `aws elasticbeanstalk describe-...`
shell commands as Bash-tool inputs that include the rendered output
as well). After `tokenizer(text, max_length=1024, truncation=True)`,
the truncation cut occurs BEFORE the assistant span. The assistant
content exists in the source data, just falls off the end after
tokenization.

**This was never caught by the v1/v2 dataset audits** because both
audits gated on "chat template renders without error" — which it
does. The audits did not model the trainer's specific masking
strategy + max_length truncation. Different scopes; gap between
them.

## What this changes for next time

- The post-incident retrain (`launch_v3.sh`) cuts iteration cost from
  ~13h-per-failure to ~75min-per-failure: NaN at first eval (step 500
  = 75 min in) triggers `NanGuardCallback`, so we never burn the full
  ~13h on broken signal again.
- The wizard / qwen-finetune skill iron-rules need updating
  (separate task #7) — rules #1 and #2 about `models/` symlinks into
  Dropbox are now obsolete; the new rule is "never let those paths
  symlink into Dropbox at all."
